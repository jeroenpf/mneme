Three ways to read Mneme

The same plan, rendered three ways — so you can pick the one you'd actually want to sit in all day. Paper is a warm editorial memo, Slate a cool modern reading surface, Ink a dark theme done right. Switch themes and switch between a document and the registry — the left rail never moves, which is the fix for the menu that used to shift under you. Nothing here touches the app yet.

Mneme · Plan · Phase 3

Search & retrieval: one ranked query over every store

Give Claude Code a single ranked query across documents, decisions, snippets, and the journal — so retrieval stops depending on knowing which store to ask first.

In progress UpdatedJul 14 Projectmneme Arearetrieval
01

Why unify search

Right now retrieval is per-type: search_documents, query_decisions, and get_snippets each answer a different question, and the caller has to know which store holds the answer before asking. That's fine for a machine with the schema memorized, but it makes the human viewer's search box lie — it only ever searches documents.

The goal is one entry point, search(q, types?), that ranks results across every content type and lets the caller narrow by type only when they want to. It leans on the same local-deployment Postgres we already run — no new infrastructure.

Decision · one endpoint, many stores

A single search() tool fans out to each store and fuses the rankings server-side. The per-type tools stay for callers that already know where to look; the unified one becomes the default the digest and the UI search box both use.

03

Ship the lexical path end-to-end first — it's useful on day one and de-risks the ranking work. Semantic recall layers on top without changing the contract.

06

Query shape

Hybrid retrieval fuses two independent rankings by reciprocal rank, so neither mode has to produce a comparable score:

sqlinternal/store/search.sql
-- Reciprocal-rank fusion over lexical + semantic
with lexical as (
  select id, row_number() over (order by rank desc) as r
  from doc_search
  where tsv @@ websearch_to_tsquery('english', $1)
), semantic as (
  select id, row_number() over (order by embedding <=> $2) as r
  from doc_search order by embedding <=> $2 limit 50
)
select id, sum(1.0 / (60 + r)) as score
from   (select * from lexical union all select * from semantic) f
group by id order by score desc limit 20;
07

Risks

  • Embedding drift — re-embedding on model change is a batch job we haven't scheduled.
  • Fusion weighting is a guess until there's real query traffic to tune against.
Watch · embedding drift

If the embedding model changes, stored vectors and query vectors stop sharing a space and semantic recall silently degrades. Pin the model id in env and re-embed on change — don't let it float.

08

Decision

Adopted · hybrid, lexical-first

Ship lexical retrieval now behind the unified search() contract; add pgvector semantic recall and RRF fusion in Phase 4 without breaking callers. Recorded in the decision log so the "why lexical first" is searchable later.
