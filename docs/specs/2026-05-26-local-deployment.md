# Local deployment with `https://mneme.local`

Mneme runs on the laptop, not on the Pi. Reached via `https://mneme.local`
with a real trusted cert and zero collision with any other Docker
projects already bound to `127.0.0.1:443`. Single Go binary serves
both HTTP/TLS and the SPA — no reverse proxy.

## Why this changed from Pi

The original plan put Mneme on a Raspberry Pi 4 at `mneme.local` for
LAN-wide access. In practice the laptop is the only client that
matters (Claude Code runs on it; the browser runs on it) and the
laptop isn't always on the home LAN. A Pi-hosted Mneme would be
unreachable from coffee shops, hotels, and any other network the
Pi-hole isn't on — the exact situations where context recall is most
useful.

Running on the laptop solves that with no remote-access machinery: the
service is wherever the laptop is. The trade-off is that no other
device — phone, iPad, second Mac — can reach it. That's acceptable;
the consumer for Mneme is Claude Code on this Mac.

## Two problems to solve

1. **Port collision.** Other parallel projects on this Mac already
   bind `127.0.0.1:443` for their own dev setups. Mneme needs a
   separate "address" without disturbing them.
2. **Browser-trusted SSL.** `Claude Code`'s HTTP client validates
   certs strictly. Self-signed warnings are off the table.

## The shape

```
┌─ macOS host ────────────────────────────────────────────────┐
│                                                             │
│  /etc/hosts: 127.0.0.2 mneme.local                          │
│  lo0 aliases: 127.0.0.1 (default), 127.0.0.2 (LaunchDaemon) │
│                                                             │
│  ┌─ other projects ──┐   ┌─ mneme docker compose ─────────┐ │
│  │ caddy / nginx     │   │ app container :8080 (TLS)      │ │
│  │ binds 127.0.0.1   │   │   ports: ["127.0.0.2:443:8080"]│ │
│  └───────────────────┘   │ postgres container :5432       │ │
│                          └────────────────────────────────┘ │
│                                                             │
│  mkcert root CA in macOS Keychain                           │
└─────────────────────────────────────────────────────────────┘

Browser → https://mneme.local → 127.0.0.2:443 → app:8080 (TLS via mkcert certs)
```

### Conflict-dodging (loopback alias)

macOS's `lo0` interface can host multiple IPs in `127.0.0.0/8`. We
add `127.0.0.2` as a secondary loopback address. Mneme's Docker
port-publish uses that as its host bind (`127.0.0.2:443:8080`), so it
never touches `127.0.0.1:443` where the other projects live. TCP
sockets are keyed by `(local_ip, local_port)` — different local IPs,
different sockets, both kernels-blessed to coexist.

### Trusted TLS (mkcert + Go-native)

[mkcert](https://github.com/FiloSottile/mkcert) installs a root CA
into the macOS Keychain (and Firefox if present) one time. After
that, `mkcert mneme.local` produces two `.pem` files that the system
trusts. The Go server reads them and calls `ListenAndServeTLS`
directly — no reverse proxy.

Reusing mkcert across other projects means the CA install is a
one-time cost shared with anything else that wants trusted local
certs.

## Components

### Go server — bimodal TLS

`cmd/server/main.go` chooses between TLS and plain HTTP based on
whether cert paths are configured + present:

```go
if cfg.TLSCert != "" && cfg.TLSKey != "" {
    if err := srv.ListenAndServeTLS(cfg.TLSCert, cfg.TLSKey); err != nil { ... }
} else {
    if err := srv.ListenAndServe(); err != nil { ... }
}
```

`config.Config` gains:

```go
TLSCert string  // MNEME_TLS_CERT, e.g. /app/.certs/mneme.local.pem
TLSKey  string  // MNEME_TLS_KEY,  e.g. /app/.certs/mneme.local-key.pem
```

When unset (default), Mneme listens plain HTTP — keeps the test
suite working unchanged and means the binary still serves on first
boot before mkcert has been run.

### Certs

Generated by `mkcert -cert-file .certs/mneme.local.pem -key-file .certs/mneme.local-key.pem mneme.local 127.0.0.2 localhost`.

Stored under `.certs/` in the repo root. `.gitignore` excludes the
whole directory. The Mac's bind-mount in compose (`./` → `/app`)
already exposes them to the container at `/app/.certs/`.

### `compose.yaml` updates

- Drop the existing `app` port mapping `18080:8080` (a plain-HTTP escape hatch from the Pi era — no longer needed since Vite can proxy to HTTPS).
- Add `127.0.0.2:443:8080` to publish the TLS port on the alias.
- Add `MNEME_TLS_CERT` and `MNEME_TLS_KEY` env vars pointing into the bind-mounted `.certs/`.
- Keep Postgres' `25432:5432` (handy for `make psql`).

### `vite.config.ts` updates

Dev proxy switches from `http://localhost:18080` to
`https://mneme.local`, with `secure: true` (mkcert cert is trusted,
so we DON'T need to bypass cert validation). `VITE_API_TARGET` env
override stays as the escape hatch.

```ts
proxy: {
  '/api':    { target: 'https://mneme.local', changeOrigin: true },
  '/health': { target: 'https://mneme.local', changeOrigin: true },
},
```

### `.mcp.json`

URL switches from `http://localhost:18080/mcp` to `https://mneme.local/mcp`.

### Loopback alias LaunchDaemon

macOS doesn't persist `ifconfig` aliases. A LaunchDaemon re-creates
the alias at boot (system domain, runs as root).

`scripts/local.mneme.loopback.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>          <string>local.mneme.loopback</string>
  <key>ProgramArguments</key>
  <array>
    <string>/sbin/ifconfig</string>
    <string>lo0</string>
    <string>alias</string>
    <string>127.0.0.2</string>
    <string>up</string>
  </array>
  <key>RunAtLoad</key>      <true/>
  <key>StandardErrorPath</key><string>/tmp/mneme-loopback.err</string>
</dict>
</plist>
```

### Makefile targets

New:
- `make setup-host` — one-time per machine. Idempotent. Steps:
  1. Verify `mkcert` and `docker` are on `PATH`.
  2. `mkcert -install` (no-op if already trusted).
  3. `mkcert -cert-file .certs/mneme.local.pem -key-file .certs/mneme.local-key.pem mneme.local 127.0.0.2 localhost` (overwrites cleanly).
  4. `sudo cp scripts/local.mneme.loopback.plist /Library/LaunchDaemons/`.
  5. `sudo chown root:wheel /Library/LaunchDaemons/local.mneme.loopback.plist`.
  6. `sudo launchctl bootstrap system /Library/LaunchDaemons/local.mneme.loopback.plist` (no-op if loaded).
  7. `sudo ifconfig lo0 alias 127.0.0.2 up` (immediate effect, no reboot).
  8. If `/etc/hosts` doesn't contain `mneme.local`, append `127.0.0.2 mneme.local`.
- `make verify-host` — non-destructive status check: `mkcert -CAROOT` present? `.certs/mneme.local.pem` exists and valid? loopback alias up? `/etc/hosts` entry present? `https://mneme.local` returns 200? Prints one line per check, green or red.

Modified:
- `make dev` — `docker compose up -d` then `cd web && npm run dev`. Same flow as before; Caddy/proxy concerns are invisible.

Removed (from the earlier Pi-era plan amendment):
- `make deploy`, `make logs-pi`, `make rollback` — there's no remote.

## Setup ceremony (the one-time bits)

```
brew install mkcert        # if not already installed
make setup-host            # installs CA, certs, LaunchDaemon, hosts entry
make dev                   # bring it up
open https://mneme.local   # browse — trusted cert, no warnings
```

After reboot: nothing to do. LaunchDaemon re-creates the alias.

After `mkcert -uninstall` or Keychain reset: re-run `make setup-host`.

After cert expiry (~2 years): re-run `mkcert ...` step alone (the
loopback alias and trust install are still good).

## Out of scope

- **Phone / second-device access.** Loopback addresses are unreachable
  from other devices by design. Future bridge: bind the app to the
  laptop's LAN IP and rely on Pi-hole / DNS for hostname resolution.
- **Production multi-stage Dockerfile.** Dev container (`Dockerfile.dev`
  + `air`) is sufficient for a single-user local tool. A trimmed
  multi-stage image is only worth the effort if we ever want to run
  the embedded binary outside Docker, which we don't.
- **Public exposure.** Mneme has no auth. Don't expose it publicly
  without a bearer-token middleware first.

## Open questions deferred

- **Cert renewal automation.** mkcert certs are valid ~2 years. A
  `~/Library/LaunchAgents/local.mneme.cert-check.plist` could nudge
  on expiry. Punt until first expiry actually happens — that's 2028.
- **Backups of the Postgres volume.** Local-only deployment means
  the laptop is the single point of failure. Cover separately when
  the data starts mattering (probably Phase 2.x).
- **Shifting Postgres' tuning.** Current tuning (`shared_buffers=256MB`,
  `work_mem=8MB`, `max_connections=20`) was sized for the Pi's 4GB
  RAM. Numbers are fine on a Mac too, but the *rationale* changes
  from "shared with Pi-hole" to "this is a personal-scale dataset, no
  reason to consume more than necessary." Update CLAUDE.md to reflect.

## Addendum (2026-07-12, during Phase 1.8 execution): `mneme.dev:8443` on
## `127.0.0.1`, not `mneme.local:443` on a loopback alias

Two macOS/Docker realities the original design didn't account for forced a
change of both the **hostname** and the **publish target**. Final shape:

- **URL:** `https://mneme.dev:8443` (was `https://mneme.local` on 443).
- **Resolution:** `/etc/hosts` maps `mneme.dev → 127.0.0.1` (was
  `mneme.local → 127.0.0.2`).
- **Publish:** compose `ports: ["127.0.0.1:8443:8080"]` (was `127.0.0.2:443:8080`).
- **Cert:** mkcert leaf for `mneme.dev localhost 127.0.0.1`, files
  `.certs/mneme.dev.pem` / `-key.pem`.
- **Dropped:** the `lo0` alias, the `scripts/local.mneme.loopback.plist`
  LaunchDaemon, and the `ifconfig lo0 alias` step. `make setup-host` now only
  installs the mkcert CA + leaf cert and writes the `/etc/hosts` entry.
- **Unchanged:** bimodal TLS in the Go server, mkcert-issued trusted cert,
  no reverse proxy, TradeGod (the other project on `:443`) untouched.

### Reason 1 — `.local` is mDNS on macOS (this was the real blocker)

macOS reserves the `.local` TLD for multicast DNS (Bonjour). A lookup of
`mneme.local` is handed to `mDNSResponder`, which issues a multicast query
and **waits ~5 seconds for it to time out before falling back to
`/etc/hosts`** — even though the hosts entry is right there. Measured with
`curl -w %{time_namelookup}`:

| Host | `time_namelookup` | effect |
|---|---|---|
| `127.0.0.1` (literal IP) | ~0 s | requests instant |
| `mneme.local` | **5.007 s, every call** | any request with a <5 s timeout fails |

That 5 s penalty — not Docker — is what made the service look broken (health
checks with `--max-time 5` timed out inside name resolution). A TLD that
isn't `.local` (`.dev`, `.test`, `.internal`, …) resolves straight from
`/etc/hosts` with no mDNS detour. We use `mneme.dev`. Note `.dev` is
HSTS-preloaded (forces HTTPS) — fine here, the service is HTTPS-only anyway.

### Reason 2 — Docker Desktop won't forward to a loopback alias reliably

Independently, Docker Desktop for Mac (Linux VM, **gVisor** networking) does
not reliably forward a published host port into the VM when the bind IP is a
secondary loopback alias (`127.0.0.2`) and it's the container's only
published host IP. Tested by IP so mDNS is out of the picture (`curl
--resolve`), hammering `/health`:

| Publish config | Result |
|---|---|
| `127.0.0.1:8443` (default loopback) | **20/20 ok**, stable across idle |
| `127.0.0.2:8443` (alias, *sole* host IP) | **0/20** — TCP connects, then reset/timeout |
| `127.0.0.2:8443` *plus* a `127.0.0.1:8443` co-mapping | works — but only because 127.0.0.1 is also published |
| `127.0.0.2:443` (alias, privileged port) | never works |

The container is healthy throughout (internal `https://localhost:8080/health`
= 200). Publishing on `127.0.0.1` is the reliable path.

### Consequence for the "conflict-dodging" rationale

The alias existed for exactly one reason: to keep host port **443** free for
other projects (TradeGod's Caddy). Once we accept a high port in the URL
(`:8443`), that collision disappears on its own — `127.0.0.1:8443` clashes
with nothing — so the alias has no remaining purpose, and TradeGod keeps
`0.0.0.0:443`. The port in the URL is the entire cost; for a single-user tool
consumed by Claude Code and a browser bookmark, that's acceptable. A clean
`:443` URL would need a host-run binary bound directly to a loopback alias
(host processes bind aliases fine; only Docker's VM forward can't) or a real
reverse proxy — both bigger than this is worth today.

> **Aside — Docker Desktop forwarding can wedge under churn.** During this
> session, heavy port-remap churn (a Docker Desktop restart plus ~10 rapid
> `--force-recreate`s with changing bind IPs, and yanking a still-published
> `lo0` alias) left the host→VM forwarder stuck even on `127.0.0.1` until a
> full Docker Desktop restart. Normal single-bring-up usage doesn't trigger
> it; if `127.0.0.1:8443` ever refuses connections while the container is
> healthy, restart Docker Desktop.
